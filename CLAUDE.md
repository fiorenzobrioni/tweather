# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

**tweather** is a planned Android weather app (Kotlin 1.9+ / Jetpack Compose Material 3) whose entire UI mimics a code editor: weather data is rendered as syntax-highlighted "files" (`weather_data.json`, `cities.json`, `settings.config`, `history.diff`) with line numbers, editor tabs, and a terminal aesthetic inspired by Obsidian/VS Code.

All four screens, the home widget, the per-city `README.md` tab and Fase 11's "Weather CI" (user-defined notification rules in `alerts.rules`, a second file behind the Settings tab bar) are implemented and verified on device (see `PLANNING.md`, phases 0 through 11b). Feature work is closed: Fase 11b was a pre-v1 restyling pass (no new features) and Fase 12 shipped **v1.0.0** as a GitHub Release (tag `v1.0.0`, 20 Aug 2026 — APK signed with the real key + R8 mapping, published automatically by `release.yml`). Design artifacts and specifications:

- `tweather_comprehensive_project_prd_final.md` — the PRD; the source of truth for features, screens, and colors.
- `obsidian_syntax/DESIGN.md` — the full design system ("Obsidian Syntax" theme): Material 3 color tokens (YAML frontmatter), typography scale, spacing, and component specs.
- `*/code.html` + `*/screen.png` — static Tailwind HTML mockups and screenshots for each screen (main editor, search, settings, logs/diff, brand logo). These are reference-only prototypes, not production code.
- `weather_data.json_sample.json` / `weather_data.json_full_sample.json` — sample data shapes the main screen renders. The full sample defines the expected weather data model (location, current conditions, air quality, pollen, astronomical, hourly/daily forecast, system info).

## Writing `README.md` (root file only)

**No em dashes (`—`) or en dashes (`–`) in the root `README.md`.** Rewrite the sentence
rather than swapping in a hyphen: a `-` standing in for a dash reads as a typo. Use a
colon when the clause explains, a full stop when the thoughts are separate, parentheses
when it is an aside.

This is a house style for the project's shop window, not a grammar rule, and it is
**deliberately scoped to that one file** — every other file in the repo, including
`PLANNING.md` and `CLAUDE.md` itself, keeps normal punctuation.

## Build and commands

Stack: Kotlin 2.2 + Jetpack Compose (Material 3), Gradle 9.1 / AGP 8.13, version catalog in `gradle/libs.versions.toml`. Package/applicationId: `com.callbackdev.tweather`. minSdk 33 (deciso a fine Fase 9: language picker di sistema per la l10n IT/EN, un solo code path per POST_NOTIFICATIONS, themed icons, java.time completo — niente fallback per Android vecchi), compile/targetSdk 36.

- Build debug APK: `./gradlew :app:assembleDebug` (output: `app/build/outputs/apk/debug/app-debug.apk`)
- Unit tests: `./gradlew :app:testDebugUnitTest` — single test class: `./gradlew :app:testDebugUnitTest --tests "com.callbackdev.tweather.SomeTest"`
- Lint: `./gradlew :app:lintDebug`
- Installable minified build: `./gradlew :app:assembleRelease -PsignReleaseWithDebugKey`
- On this machine there is no system JDK: prepend `JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"` (Android Studio's bundled JDK) to gradlew commands.

**Debug signing**: `keystore/debug.keystore` is intentionally committed (alias `tweather-debug`, store/key password `android`) so debug APKs from CI and any machine share one signature and can update an existing install. Do not regenerate it. Debug builds carry `applicationIdSuffix ".debug"` and the launcher label `tweather (dev)` (debug res overlay), so they install **side-by-side** with the release-signed app — series decision (Aug 2026), same as snake. The debug-signed *release* build (`-PsignReleaseWithDebugKey`) keeps the plain id: it exists for pre-release smoke tests, not for daily side-by-side testing.

**CI**: `.github/workflows/android-ci.yml` runs on every push — unit tests, lint, then both APKs. Artifacts: `tweather-debug-apk`, `tweather-release-apk-testing-only`, `tweather-release-mapping` (the R8 map, needed to read a release stack trace), plus `app/build/reports/` on failure. Tests run *before* the builds so a red suite never produces an installable artifact.

**Release signing** (Fase 12): the real keystore lives OUTSIDE the repo (`C:\Fiorenzo\keys\tweather-release.jks`); the `release` signingConfig is created only when the four `TWEATHER_KEYSTORE*` properties are all set — from `~/.gradle/gradle.properties` locally, from `ORG_GRADLE_PROJECT_*` env vars (GitHub Secrets) in CI — and wins whenever configured. On an unconfigured checkout the release build is unsigned by default (`app-release-unsigned.apk`); passing `-PsignReleaseWithDebugKey` signs it with the committed debug key so the minified build is installable for testing — R8 breakage shows up nowhere else. That flag stays opt-in precisely so an unconfigured checkout can never produce an installable release by accident. `.github/workflows/release.yml` fires on `v*` tags: tests + lint, then the real-key APK published as a GitHub Release together with its R8 mapping.

**Alert engine** (Fase 9c): background notifications via a single WorkManager periodic job (`weather-sync`, interval = `update_frequency_min`, now 15/30/60/120 default 60, CONNECTED-only constraint, no foreground services/exact alarms/FCM/background location). Pure rules in `domain/AlertEngine.kt` (severe WMO buckets 12h, precip ≥70% 6h, daily summary 06–12), dedup fingerprints in DataStore `alerts`, notification body rendered as a JSON object (localized title, English keys and command line, localized data values via `WeatherTranslations` — same l10n rule as the main screen and the widget; folded onto one line when collapsed, pretty-printed when expanded). Background fetches write Logs commits like any fetch.

**Weather CI** (Fase 11): user-defined notification rules in `alerts.rules`, the second file behind the Settings tab bar. Pure engine in `domain/rules/`: a curated variable registry mirroring `weather_data.json` names with explicit time namespaces (`current.*`, `next_6h.*`/`next_12h.*` precomputed aggregates, `today.*`), 1–2 conditions joined by a single `and` (no `or`/parentheses — two rules instead), thresholds stored metric and rendered in the user's units (name included: `temp_c` ↔ `temp_f`). No parser anywhere: rules are edited token by token (inline variable picker, operator cycles, threshold/name/message become terminal inputs), so a syntax error is not writable. Anti-noise: `current.*`-only rules are edge-triggered (fire on false→true, re-arm on false), rules reading forecasts dedup per half-day fingerprint; state in DataStore `rule_state`, cleared per rule on condition edits. Evaluation piggybacks on the existing `weather-sync` fetch (zero extra battery); fired rules land on the commit (Room v3 `fired_rules`) and render as `✓ rule "x" fired` check lines in the Logs. Dry run via `$ tweather run rules` (two-tap): stateless per-rule results inline, nothing posted. Master toggle `notifications.user_rules` (default true); builtin alerts deliberately stay as plain `settings.config` toggles.

**Offline / a failed update** (Fase 17): the editor never blanks. A fetch that fails falls back to `ReportDiskCache`'s last successful response for that city (`WeatherRepository.cachedReport`, no TTL), which carries a **week** of forecast — so yesterday's fetch still holds today. `domain/WeatherRecency.kt` is the companion to `WeatherFreshness` (freshness = whether to trust it, recency = which rows have not already happened): it drops elapsed hours and days in the city's zone, so `## Next hours` never opens with hours that are over and `## Today` is today, and `coversNow` is the fallback's expiry — read off the data (does the forecast still reach the present?) rather than from a constant. The state carries `staleFor`, printed above the document in each file's register (a sentence in `README.md`, `// stale: last good fetch 3h ago` in the JSON, `WeatherFreshness`'s 2× interval as the threshold — the same one the widget has marked `# stale` with since 9d). A recovered document passes the REAL now to `toReadmeMarkdown`, or `## Status` would search a window that has closed and answer "everything looks good". `README.md`'s state lines are prose and localized (`WeatherStateProse`) while the JSON keeps `net::ERR_*`: same split as everywhere else.

**First run** (Fase 14b/14c): a fresh install has **no seeded city** — `cities.json` listing a place the user never chose was the last lie left in the product. "No location" is a real state (`ActiveSource.None`): the editor says `// no location configured`, the FAB hides, the widget keeps its `# no data yet` render, worker and engines exit early, and the last city can be removed. Installs that predate it keep what they were watching — `CityStore.migrateFirstRun(hasHistory)` runs once and tells a used install from a fresh one by whether the Logs have any commit. First run is `$ tweather init` (position / search / skip), deliberately one screen and not a carousel; it and the `HELP.md` hint are **localized**, the same exception `README.md` makes, because they are the two surfaces addressed to someone who doesn't read the app yet.

**GPS current location** (Fase 9b): the device position can be the active weather source — platform `LocationManager`/`Geocoder` only (no play-services), `ACCESS_COARSE_LOCATION` only, GPS pseudo-city with reserved id `-1L` kept out of the saved list, toggle in `settings.config` (`location.use_gps`), pinned `current_location.json` entry in `cities.json` (tertiary color).

**Sky module** (Fase 16): `sky.crontab`, the third editor tab, is what the sky above the active city has scheduled next, written as a real crontab — the recurrence in the cron field (`@daily`, `@yearly`, a polling expression), the computed instant in the comment channel, because a fixed minute field would be a grammar the file cannot keep. Pure engine in `domain/sky/`: Meeus's series in `AstronomyMath`, one altitude-crossing primitive in `AstronomyEngine` for every solar and lunar event (sunrise is that crossing at −0.833°, civil dawn at −6°, the golden hour a range), a fixed `SkyJobCatalog` of 32 jobs edited token by token like `alerts.rules` (no parser anywhere), meteor peaks pinned to **solar longitude** so the table never expires, and `SkyVerdictEngine` turning the hourly forecast plus the moon into `✓ pass` / `~ unstable` / `✗ fail` / `? unknown` with the number it used printed beside it. `SkyAlmanac` memoizes per (city, local date) — measured, not precautionary. One engine feeds the crontab, `weather_data.json`'s `astronomical` block and the README's `## Astronomy`, so the app cannot show two sunrises for one city (there is an agreement test). The dotted job ids are code and stay English everywhere they are printed — except in the README, which prints none of them: its `## Status` line looks the job up in `ui/sky/SkyJobNames.kt` and says the verdict as a localized sentence, number included (Fase 16g), because that document is prose. Runs are recorded on the **existing commit row** (Room v4, one nullable `sky_runs` column, exactly like `fired_rules`) rather than in a table of their own: a run is something a fetch noticed, and `obs +12m` is then implied by the schema. Gated on `sky.enabled`; the whole schedule is local computation and works offline.

**Reminders** (Fase 16f) are the module's only new scheduling primitive: one `AlarmManager.setAndAllowWhileIdle` alarm at a time for the nearest `--notify` lead, never `setExact*` and deliberately **no `SCHEDULE_EXACT_ALARM`** (hence a 15-minute floor on the leads and no `5m` in the cycle), re-armed after every fetch, after every edit, when one fires and on `BOOT_COMPLETED`. `notify_default` in `settings.config` is the lead a line uses when it carries none of its own (**not** a seed copied into new jobs: every line stores null until tapped, so a seed would leave the `--notify` column unreachable) and defaults to `off`. Dedup fingerprints in DataStore `sky_alerts`, occurrence identified to the minute. `notify_on_fail` (default false) decides whether a `✗ fail` still notifies; `? unknown` is sent for events that happen regardless of the sky and suppressed for the visibility-dependent ones. Only the active city schedules reminders, never a widget-pinned one.

Full spec and every decision in `VISION_SKY.md`.

**Decided (overrides the PRD's OpenWeatherMap example): the weather provider is Open-Meteo** — free, no API key. Forecast API for current/hourly/daily + astronomy, Air Quality API for AQI/pollutants/pollen (pollen is Europe-only), Geocoding API for city search. Moon phase is not provided and must be computed locally. See `PLANNING.md` (Fase 3) for details; `PLANNING.md` is the phased implementation plan with checkable steps — keep it updated as work progresses.

## App structure (per the PRD)

Four screens, each presented as a fake "file" behind a bottom navigation bar (Editor / Search / Settings / Logs — the first tab was labelled "Explorer" behind a file-tree glyph until Fase 11b; its nav route is still `"explorer"`):

1. **Main editor** (`weather_data.json` + `README.md`) — live weather rendered as formatted JSON with syntax highlighting and a line-number gutter; refresh via a glowing FAB. A second editor tab (Fase 10) shows the city's `README.md`: the human summary as highlighted markdown *source*, fully localized (headings included — it's prose, the keys-stay-English rule doesn't apply), with `## Status` fed statelessly by the AlertEngine. Since Fase 11c it also carries the hourly forecast (`## Next hours`: since 11e, 14 rows of hour/temp/rain/status starting at the hour AFTER the current one — the current hour is `## Current`'s job, rain probability on the feels-like line; the full 24-hour run with its technical fields stays the JSON's, and since 11f the JSON too starts at the hour after the current one — the mapper carries 25 slots, slot 0 feeding `current_conditions` and the engines, so `hourly_forecast` still shows 24 rows), and both its tables are padded to their column widths with exactly one weather emoji against each cell's left edge, description after it (right edge and emoji-only hourly status until Fase 11d): the emoji are missing from JetBrains Mono and come from the system font, so a fixed one-per-cell position is what keeps the columns true whatever that glyph measures. Both tables put the status column last, so the numeric columns never pan off-screen and a long description clips instead of hiding data. Since Fase 16c a **third tab** is `sky.crontab`: what the sky above the active city has scheduled next (sunrise, golden hour, the dark window, a shower's peak), as a real crontab — the recurrence in the cron field, the computed instant in the comment channel. Edited token by token like `alerts.rules`, no parser; gated on `sky.enabled` in `settings.config`. The active tab persists in the `workspace` DataStore (editor workspace state, deliberately not a `settings.config` key). The `⎇ <city>` in the status bar is tappable (VS Code's branch switcher) and jumps to `cities.json`.
2. **Search / cities** (`cities.json`, Fase 10b — it absorbed the old `cities/` Explorer screen) — the input field is the `"search_term"` JSON property; geocoding results while typing; `"saved_cities"` is the array of saved cities as fake filenames (GPS entry `current_location.json` pinned in tertiary, active city in primary + `// active`, removal via `[rm]`); recent searches as a JSON array.
3. **Settings** (`settings.config`, `alerts.rules`, `HELP.md`) — booleans as toggles, theme profiles (Obsidian, Dracula, Monokai). The third file (Fase 14d) is the app explained to someone who doesn't read `git` for a living: the four tabs, the borrowed words (commit, diff, branch, CI), where the data comes from, one paragraph on why it looks like this. Prose, so fully localized like `README.md`; a one-off `// new here? open HELP.md` line heads the editor until the file has been opened (state in the `workspace` DataStore, deliberately not a `settings.config` toggle — a switch for a one-time hint would outlive its purpose and `$ tweather reset settings` would bring it back).
4. **Logs** (`history.diff`, `forecast.diff`, `sky_runs.log` — the two `.diff` were `weather_history.diff`/`weather_forecast.diff` until Fase 16f: the `weather_` prefix was the app's only such prefix and cost the three-name tab strip the 16 characters it needed to fit a 360dp screen; `docs/screenshots/` still shows the old names) — each data fetch is a git-style "commit" with hash and author `sys@tweather.app`; changes shown as `+`/`-` diff lines. The third file (Fase 16e, gated on `sky.enabled`) is the sky module's journal: outcomes, not changes, which is why it is a `.log` and not a `.diff`.

## Design constraints (non-negotiable per the design system)

- **Typography**: JetBrains Mono everywhere, 4px baseline grid, 20px indent per nesting level. The **home widget is the single exception** (Fase 9d): since CVE-2021-0567 the launcher inflates widget layouts in a restricted context that silently drops `@font/` resources, so its layouts use the system `monospace` family. Glance has the same limitation; the only workaround would be rasterizing text to bitmaps, which costs system font scaling and TalkBack. Decided with the committente.
- **Syntax highlight colors**: keys `#79c0ff`, string values `#a5d6ff`, numbers/booleans `#ffa657`, comments/braces `#8b949e`, diff additions `#2ea043`, deletions `#f85149`.
- **Core palette**: background `#10141a`, surface container `#181c22`, on-surface `#dfe2eb`, borders `#30363d`. Full Material 3 token set is in the `obsidian_syntax/DESIGN.md` frontmatter.
- **No drop shadows** — depth comes from 1px borders and tonal stacking. The only exception is the FAB's glow (`box-shadow: 0 0 15px #79c0ff88`); every element, FAB included, is rectangular with a 4px corner radius (the FAB was circular in early revisions — squared during development, nothing in an editor is round).
- **Controls rendered as text**: booleans as tappable `true`/`false` values, removal as `[rm]`, destructive actions as `$` commands with a two-tap confirm, inputs as terminal prompts (`> Search Location _` with blinking underscore cursor). No native Material controls anywhere.
- **Localization rule — three registers** (Fase 18, series-wide): the **register** decides the language, not the punctuation around it. **Code** is always English: JSON keys, filenames, job ids, rule variables and operators, cron fields, `$` commands, git chrome (`commit`, `Author:`, `@@`, hashes), verdicts (`✓ pass`, `~ unstable`, `✗ fail`), log levels (`ERROR:`, `WARN:`), error codes (`net::ERR_*`), licenses, URLs. **Data** localizes: weather values, city names, day names, moon phases. **Prose** localizes wherever it appears — `README.md`, `HELP.md`, first run, notifications, accessibility text **and the comment lines that are sentences** (`// tap to enable`, `// hint: …`, the `sky.crontab` notes). Two tests, in order: would translating it break a lookup, a filename, a copy-paste or the alignment with a key printed elsewhere (→ code), and would `git` translate it (it translates "nothing to commit, working tree clean" and never `commit`). A single line can hold both registers — keep the tokens and translate around them (`// ERROR: permesso negato — il gps resta spento`). One-word markers (`# stale`), file banners (`// Tweather Configuration File`) and the `GET`/error-code lines stay English. This **replaces** "`//` comments stay English" (Fase 6b), which mistook the channel for the register; it applies 100% or not at all, because a rule kept four times out of five reads as a half-finished translation. **Implementation is a phase of its own and has not run yet** — the comment strings in this repo are still English in code.
- Weather icons are inline Unicode emoji inside the JSON text (`☀️`, `🌧️`, `🌔`), not image assets.
